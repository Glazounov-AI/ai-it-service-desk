# F3.6 — persistent ticket drafts

Managed diagnostics automatically builds a draft in the same SQLite transaction as the diagnostic case, assistant response and final session status. The user message remains separately persisted as before. One draft per session, unique ticket ID. GET /sessions/{id}/ticket-draft reads the snapshot; POST returns the existing snapshot or creates one for a previously escalated session. No external submission. Closed sessions retain existing drafts. No new dependencies.

TS-022: narrowly matched explicit retrospective report of reconnecting and checking another resource, with continued failure and request for escalation. Only those two actions are recorded as completed. The VPN troubleshooting_completed field means both remediation checks failed, not that every information collection action was performed. Missing resource names remain explicit (D18). Other wording is not guaranteed to match. No new LLM calls for draft construction. Existing diagnostic flow remains opt-in. Existing admin regression now expects ticket_draft_ready instead of escalation_required.

Drafts are immutable snapshots. No authentication or external ticket integration; local development only. Existing safety filtering is not a guarantee against all secrets. Preliminary regression: 120 passed on Python 3.13.5, mocked upstream. Target Python 3.14.4 and live integration pending.
